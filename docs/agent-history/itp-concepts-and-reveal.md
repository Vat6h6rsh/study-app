## 1. Make the "Explain code" comments work for an ABSOLUTE BEGINNER
The current comments are good: they narrate the program flow ("this pointer now holds the address of...", "the for loop checks the condition, runs the body, then goes back and checks again", "this command prints..."). KEEP that step-by-step narration of what happens and in what order. ADD the concept behind it, written for someone who has never programmed before: plain English, no unexplained jargon (if a term like pointer, address, index, condition, return value or null terminator appears, explain it in a few words the first time it appears in that program), concrete values from this program where possible ("first time round, i is 0, so..."), and WHY the line is needed. Examples of the target tone:
- `// The loop starts with i = 0. Before each round it checks i < 5; if that is true the body runs, then i++ adds 1 and it checks again. When i reaches 5 the check fails and the loop ends.`
- `// % gives the remainder after dividing. 153 % 10 is 3, so this grabs the last digit (our numbers are base 10).`
- `// &x means "the address of x" (where x lives in memory). scanf needs the address so it can put the typed number into x.`
- `// p holds the address of box. p->width means: go to the struct p points at and use its width. It is shorthand for (*p).width.`
- `// Strings end with a hidden '\0' character that marks "stop here"; without it printf("%s") would keep reading past the text.`
Rules: placed above the line/block it explains, matching indentation; usually 1-3 short lines each; 8-18 comments per program so the whole flow is covered from top to bottom (includes, main, variables, each loop/condition, each function call, output, return 0); accurate; never state a blank's accepted answer verbatim and never give it away indirectly (explain the idea and what the line must achieve, not the exact token). Apply to EVERY ITP blanks question (all pools incl. mocks). Keep the existing data schema; keep verify-content's leak check passing.
