## 1. Two-pane layout for "blanks" questions (practice view)
- LEFT pane = the program window: the full C program in a code block, monospace, original indentation and formatting preserved exactly, line numbers (decorative, aria-hidden), horizontal scroll inside the pane only. - RIGHT pane = the answer window: a list of 10 normal single-line text boxes labelled "Blank 1" ... "Blank 10" (label visible), monospace input text, autocomplete/autocorrect/autocapitalize/spellcheck off.
  - Password-style UX as the lead: each box has an EYE toggle button inside the right edge of the field (like "show password"), aria-label "Reveal answer for Blank N" / "Hide answer", aria-pressed.   - Hovering/focusing a blank input highlights the matching `Blank N` chip in the program pane (and vice versa: clicking a chip focuses its input). Scroll the chip into view inside the code pane when its input is focused.
- Panes: side by side on wide screens (program ~60-65%, answers ~35-40%; answers pane sticky so it stays visible while scrolling long code). ## 2. Comments toggle (explanations of the program)
- Add a switch toggle at the top of the program window: "Explain code" (role="switch", aria-checked, label visible, remembered in localStorage with try/catch). ON shows explanatory comments in the program; OFF makes them completely invisible (not rendered/hidden from AT), and the code reflows back to normal.
- Comments explain what each line or block does: C syntax (what `#include`, `int main`, `scanf("%d", &x)`, `->`, `malloc` etc. mean) and the logic/flow of the whole program (what the loop is for, what is being accumulated, why this condition). Render them as C-style `// ...` comment lines placed above the line/block they describe, matching indentation, in a muted comment colour (AA contrast in all 4 themes), so it still looks like a real well-formatted program. Never put a comment inside a blank and never state a blank's answer literally in a comment (describe the intent, e.g. "loop condition: keep going while i is a valid index" rather than "i < n").

Accuracy matters: they are what the student learns from.
